# 团队文档归档系统（全量文档库）技术方案 + Spec

> 状态：决策已闭合（wayfinder 地图 #3，票 #4/#5/#6/#7/#8 全部决议）。
> 本文是把地图决议 + 五份研究报告收敛成可直接进入开发的 spec。
> 决策依据的完整出处见 `docs/research/` 五份报告与 GitHub issues #3–#8。

## 1. 目标与边界

### 1.1 目标

把团队日常沟通中接收和生成的文档统一归档、索引、转 md、建统一图片库、录入向量库，提供飞书/局域网查询入口，解决「记得处理过但忘了存在哪」的痛点——把平均 40 分钟的查找压到秒级。

### 1.2 本轮范围（第一阶段 · 全量文档库）

团队工作流的**第一步**：全量文档库，目标是「快速找到已有资料」。

- 输入：微信另存的文档（PDF/Word/PPT）、扫描版 PDF、图片、视频
- 按日期保存 → 建全量原文索引（去重）→ 统一转 md → 统一图片库 → 向量库 → 分类 → 查询

### 1.3 明确不做（Out of scope）

- **项目事实库 / 专人信息提取**：团队工作流第二步，另开图
- **本地硬件采购与自建部署**：测试靠谱后的第二阶段，另开图
- 编辑距离模糊搜索（用混合检索 + 同义词替代）
- 企业微信会话内容存档（需 Windows/Linux 采集机，本机无企业微信）
- 直接解微信容器 DB（TCC 拦截 + 法律风险，chatlog 已因法务函删除）
- 视频音轨转写 ASR
- pplx-embed-v2-late 进主线（ColBERT 多向量不兼容 WeKnora，留第二阶段）

## 2. 硬件拓扑（分阶段）

### 2.1 第一阶段（开发测试期）：全云端

| OCR（扫描件） | 本机 RapidOCR 离线（一期）；WeKnora 已配 `qwen3.8-flash`（VLM，二期接入做增强） |

> 说明（2026-11-06 用户拍板）：WeKnora 实例里已配好阿里云百炼四件套（embedding/问答/重排/视觉），全部沿用现有配置，不改。spec 早期写的 bge-m3 / GLM-4V-Flash / PaddleOCR-VL 作废，统一用 WeKnora 已配模型（**caption 例外**：2026-11-06 #14 补充拍板改为独立视觉模型，见下一条）。
>
> 一期（#13）先落地**本机 RapidOCR**：转换要能离线跑、不依赖 WeKnora 在线。qwen3.8-flash VLM 作为增强，等 #15/#16 接入 WeKnora 后再接（见 `docs/adr/0001`）。
>

## 3. 软件架构

### 3.1 组件

```
微信另存目录 ──► 摄入器 ──► SQLite（真相源）
                          │
                          ├─ 文档/版本/出现（复用 014 模型）
                          ├─ 图片库（IMG-####）
                          ├─ 视频（VID-####，人填简介）
                          └─ 项目/类别标签
                     
转换器（pandoc / OCR / markitdown）──► md + 抽出的图片 ──► 归档 + 图片库

WeKnora（云端）── 向量库 / BM25 检索 / 飞书渠道 / 问答
        ▲
        │ 派生：SQLite 里的正文 + caption 文本 → 分块 → text-embedding-v4 向量
        │
查询入口：飞书机器人（WeKnora 原生渠道）+ 局域网 Web UI
```

### 3.2 核心纪律（继承既有项目，不重造）

1. **真相源 = SQLite + 图片文件**；向量库/WeKnora 索引是**派生可重建**的。这条纪律来自 022 的 ADR-0007——「双源漂移是此前几套方案反复失败的头号原因」，以及 014 的 ADR-0001「数据库唯一真相源，导出物只读」。
2. **LLM 在应用之外**：模型调用、密钥、提示词变更频率远高于业务代码，混在一起会把「检索一条记录」的测试拖进「模型今天抽得准不准」。传输层用管理命令而非 HTTP（022 ADR-0008 实测本机 curl 被网络策略阻断）。
3. **去重永远不以人定**：指纹只做建议，最终以人工判定为准（014 ADR-0001）。

## 4. 数据模型

### 4.1 实体

在 014 三层身份模型上**扩展**（不推翻），新增图片/视频两个独立顶层实体。

**复用 014 的四类实体（字段不变）**：

| 实体 | 含义 | 关键字段 |
|---|---|---|
| **出现 Occurrence** | 一份文档在某个来源的一次现身 | source_type（wechat/zip/feishu/manual）、source_path、file_name、size、byte_hash、text_fp、status（pending/archived/merged/ignored） |
| **文档 Document** | 去重后的逻辑实体 | title、project_id（**单归属**）、current_version_id、category |
| **版本 Version** | 一段具体内容 | document_id、byte_hash、text_fp、archive_path、markdown_path（转换出的 md，相对受管目录） |
| **项目 Project** | 文档归属的业务项目 | name |

**新增两类顶层实体**：

| 实体 | 含义 | 关键字段 |
|---|---|---|
| **图片 Image** | 去重后的独立图片实体 | `IMG-####`（内容 sha256 去重、永不改号）、名称、sha256、字节、扩展名、原始名、来源、caption（VLM 生成）、尺寸、主归属项目 |
| **视频 Video** | 视频实体 | `VID-####`、名称、sha256、字节、扩展名、简介（**人填**）、时长、来源、主归属项目 |

图片库字段继承 031 的 ADR-0001/0002：`IMG-0001` 起四位数字按内容 sha256 去重后顺序分配，ID 与内容绑定、永不改号、永不复用，单一母本 + 登记表，引用只认 `{{IMG-0001}}`。052 的登记表就是真相源的 `images` 表（不再另存 031 的 `索引.tsv`，避免双源漂移）。

### 4.2 关联关系

| 关联 | 表达 | 说明 |
|---|---|---|
| 文档 ↔ 图片 | `document_images`（document_id + image_id + 内嵌/独立标记 + 位置） | 内嵌图（文档转 md 时抽出）与独立图（微信收到的截图）都要记 |
| 图片/视频 ↔ 项目 | **单归属 + 关联项目标签** | `images.project_id` / `videos.project_id` 是主项目，关联项目挂 `image_project_tags` / `video_project_tags`，与文档同一套语义；主归属一旦定下，后来的登记不改 |
| 图片溯源 | Image 的 `来源` 字段 | 记「从哪个文件抽出来」，与关联表用途不同（溯源 vs 导航） |
| 文档 ↔ 关联项目 | **单归属 + 关联项目标签** | 文档有一个主 `project_id`，其他关联项目作为多值标签挂在旁 |
| 视频 ↔ 项目/文档 | 同文档（单归属 + 关联标签） | 视频与文档平级独立实体 |

### 4.3 物理形态

- **SQLite 数据库**：单一真相源，所有实体（文档/图片/视频/项目/关联）都在库里。
- **图片/视频二进制**：文件系统（开发期）或 COS（云端），SQLite 存 URL/路径。
- **md 派生物**：每个版本转出的 md 与受管文件同位（`doc-<ID>/v<版本ID>-<文件名>.md`），路径记在 `versions.markdown_path`；图片母本统一放 `archive/images/IMG-####.<ext>`，视频母本放 `archive/videos/VID-####.<ext>`，`images.path` / `videos.path` 存相对受管目录的路径。
- 关联项目标签的存法（JSON 列 vs 独立 tag 表）与 WeKnora 标签映射，见 §6.3。

## 5. 摄入与去重管道

### 5.1 摄入

**微信手动存**：延续 014 的 `001-按日期缓存` 另存模式。不解微信容器 DB（TCC 拦截 + 法律风险）。用户把文件另存到普通目录，摄入器扫描。

### 5.2 去重（三层指纹，继承 014）

1. **byte_hash**（sha256 字节哈希）：判「字节完全相同」。
2. **text_fp**（正文归一化指纹）：判「内容相同但字节不同」（如飞书反复导出）。docx/pdf 用 textutil/anydoc 提取正文后算哈希。
3. **name_key**（文件名归一化）：指纹不同但名称相似，提示「可能是新版本」。

**去重纪律**：指纹只做建议，最终以人工判定为准。微信的 `(1)` 后缀是「同名避让」不是第二份副本，**永不按文件名去重**（微信原生去重键是 size + MD5）。

### 5.3 归档

入库 = 复制进受管目录（不动原件），按文档 ID + 版本组织。这是「下次找文件」的唯一去处。

## 6. 转换、图片库、分类

### 6.1 文档统一转 md

| 源格式 | 转换器 | 说明 |
|---|---|---|
| docx | pandoc 3.5 | 表格/图片/OMML 公式/脚注/多级标题；页眉页脚丢失（可接受） |
| 文本型 PDF | markitdown（PyMuPDF 判文字层、补页面文字） | 表格结构可能丢失，需人工校形；内嵌图按页抽出进图片库 |
| 扫描版 PDF | 本机 RapidOCR 离线（一期）／qwen3.8-flash VLM（待 WeKnora 接入） | 无 OCR 则无文本进索引；图文混排时只 OCR 无文字的页 |
| pptx | python-pptx（读文本/表格/图片/图表） | pandoc 无 pptx reader |
| xlsx | markitdown | 公式不求值 |
| .doc | textutil 转 docx → pandoc | 仅 macOS（textutil）；Linux 上不支持 |

转换后 md 与受管文件同目录（`doc-<ID>/v<版本ID>-*.md`），转换时抽出的图片进图片库，md 里对图片的引用一律改写成 `{{IMG-####}}`，不留临时媒体路径。

### 6.2 统一图片库

- **文档内嵌图**：转 md 时用 `--extract-media` 抽出 → 进图片库（sha256 去重分配 `IMG-####`）→ 生成 caption。
- **独立图**（微信截图等）：直接进图片库。
- **引用只认 `{{IMG-0001}}`**，文件名与 ID 永不变，改名只改登记表的「名称」列。

### 6.3 分类（WeKnora 标签）

**沿用 014 五类 + 项目，全部建成 WeKnora 标签**（`custom_metadata` 不能检索过滤，已核 WeKnora 源码 `SearchParams` 只有 `knowledge_ids`/`tag_ids`）。

五类（014 ADR-0002 论证，一级粒度、全项目可用）：

| 类别 | 覆盖 |
|---|---|
| 研发 | 需求/方案/设计/接口与数据协议/图纸/源码 |
| 测试 | 测试大纲/报告/试验/评审 |
| 管理 | 计划/纪要/索引/台账/进展 |
| 商务 | 合同/报价/审价/资质/函件，含合同性技术协议 |
| 资料 | 设备手册/规格书/标准/论文/彩页 |

**标签维度**：项目（主归属 + 关联项目）、类别（五类）、图片/视频（独立成类，便于「查所有图片」）。项目/类别/图片/视频四类标签的命名与多值语义在 spec 定稿时细化。

## 7. 向量库与检索

### 7.1 检索架构（第一阶段）

- **纯文本检索**：WeKnora dense（`text-embedding-v4`，2048 维）+ BM25（ParadeDB 自带 jieba）。
- **图片后置 caption**：图片不进向量库，caption（文本）走普通检索。caption 由独立的视觉模型生成（一期 GLM-4V-Flash，见 `docs/adr/0002`），失败的图仍按编号/项目可查。
- **视频**：人写简介，简介文本走普通检索。

### 7.2 embedding 选型

**WeKnora 已配 `text-embedding-v4`（阿里云百炼，2048 维）**。用户拍板沿用现有配置，不改。换 embedding 模型需重建索引，所以维度和模型从第一天定死。

### 7.3 检索能力

- **精确**：BM25 关键词（ParadeDB 自带 jieba，中文分词强于 SQLite FTS5——后者中文 2 字查询失效）。
- **模糊**：混合检索（BM25 + 向量 RRF 融合，默认 0.7/0.3）+ 同义词标签兜底；不做编辑距离。
- **自然语言**：向量语义检索。

### 7.4 两种「查」必须分开（功能缺口，已补）

| 能力 | 命令 | 返回 | 数据来源 | 阶段 |
|---|---|---|---|---|
| **内容检索** | `/search <关键词>` | 包含关键词的原文片段 + 来源文档 | WeKnora（派生索引） | 第一阶段 |
| **文件定位** | `/find <标题/文件名>` | 文档在不在、现行版本受管位置、全部出现历史 | SQLite（真相源） | **第二阶段（延后）** |

两者**不能合并**：「文件在哪」是元数据事实，必须从真相源 SQLite 拿，不能从派生的向量索引里拿。014 已有 `cmd_find` 逻辑（标题/文件名模糊匹配 → 现行版本 `archive_path` + 全部出现记录）。

**第一阶段文件定位走离线**：`track.py find` 命令行 / 迁移后 SQLite 直查兜底，不进飞书/Web 查询入口。`/find` 命令等主线功能开发测试完成后再开发（票 #9 决议）。

## 8. 查询入口

### 8.1 飞书机器人（主入口）

- **WeKnora 原生飞书渠道**（`platform: feishu`，websocket 长连接），零自建代码。
- 所需凭证（飞书开放平台自建应用）：`app_id`、`app_secret`、`verification_token`、`encrypt_key`。
- 交互命令：
  - `/search`（内容检索，混合检索返回原文片段，**不经 AI 总结**，最多 5 条、每条 200 rune + 匹配度）
  - `/find`（**文件定位，第二阶段开发**：查 SQLite 返回「在不在 + 受管位置 + 出现历史」，见 §7.4 与票 #9；第一阶段用 014 `cmd_find` 命令行兜底）
  - 自然语言问答（附赠）
- 服务范围：先私聊，跑通后群聊（群聊涉及 @机器人、话题回复）。
- **执行后置**：建应用的开权限清单写进接入步骤，不阻塞主线。

### 8.2 局域网 Web UI（辅入口）

WeKnora 自带前端，绑到内网 IP。

### 8.3 与 lark-cli 的关系

本机 lark-cli（现有应用 `cli_a9424281a5389bb6`，bot ready）与 WeKnora 飞书渠道是**不同身份**（应用凭证 vs 用户授权），不互用。lark-cli 保留作开发期手动调试工具。

## 9. 014 数据迁移

- **全量迁移**：documents / versions / occurrences / projects 四类都迁（出现记录是去重基准，5316 条仅 3.1MB，无理由删）。
- **独立建库、只读导入**：不改 014 原库（它还在跑，有飞书扫描、看板等功能）。
- **指纹复算校验**：用 014 的指纹算法重算一遍，对不上的列清单人工看（既能发现 014 指纹算法 bug，又能回退——新库作废重来不伤 014）。

## 10. 已知硬约束（实测，非假设）

| 约束 | 影响 |
|---|---|
| 无 Docker（连容器运行时都没有） | 本地跑不了 WeKnora 标准 Compose；这是选云端 Lighthouse 的直接原因 |
| ARM64 不兼容 ParadeDB x86-64-v2 镜像 | M5 Pro / M6 跑不了默认向量库镜像 |
| SQLite FTS5 中文 2 字查询失效 | trigram/unicode61 均 0 命中；关键词检索必须靠 ParadeDB BM25 |
| Perplexity/OpenAI API 网络不通（DNS 污染） | 只能用国内直连：SiliconFlow/DashScope/智谱/腾讯云 |
| 腾讯混元 GetEmbedding 2026-12-21 下线 | 不要基于它设计新系统 |
| pplx-embed-v2-late 是 ColBERT 多向量 | 不兼容 WeKnora 的 pgvector/VectorDB；留第二阶段自托管 |
