# ADR-0003：真相源 → WeKnora 派生索引

- 状态：已接受
- 日期：2026-11-06
- 相关票：#15（WeKnora 派生索引接入）、#13（转 md）、#14（媒体实体）

## 背景

到 #14 为止，真相源里已经有：文档现行版本转出的 md（`versions.markdown_path`）、
图片 caption、视频简介，以及项目/类别/媒体四类归属。WeKnora 侧只需要一个
「能按自然语言搜到正文片段」的索引——按 spec 的纪律，它是**派生、可重建**的，
删了不影响真相源。

接入要回答四件事：推什么、怎么切、标签怎么表达、重跑怎么办。

## 决策

**1. 推「知识条目」，不推外部分块。**
一份文档（现行版本的 md）、一张图（caption）、一个视频（简介）各成一条知识；
真正分块交给 WeKnora（默认 512 字符，还会做父子块与上下文补齐）。我们在外面先
切碎，只会破坏它的上下文补齐，而且两套切法迟早对不上。

**2. 标签是扁平的，四维编码在名字里。**
WeKnora 的 `KnowledgeTag` 只有 `name` / `color` / `sort_order`，没有维度字段，
所以约定：`项目/<项目名>`、`类别/<类别名>`、`图片`、`视频`。主归属和关联项目
标签都进「项目」维度；用前缀既能表达维度，又能按 `项目/` 前缀筛。

**3. 用 `POST /knowledge/manual` 推 markdown，不上传原文件。**
真相源里已经有转好的 md；再上传 docx/pdf 会让 WeKnora 自己解析一遍，既浪费，
又可能和我们的转换口径不一致（比如扫描件的 OCR 走的是本机 RapidOCR）。
manual 接口直接收 `title` + `content` + `tag_ids`，正好对上知识条目。

**4. 重跑必须显式。**
同名知识库已存在时 `index` 直接报错，要重来加 `--rebuild`（删掉同名 KB 从零推）。
不保存「已推送」的增量台账——台账会变成第二真相源，正是 spec 要避免的双源漂移；
索引的正确状态永远是「按真相源重建一遍」。

**5. 认证用账号密码换 JWT，不走 API Key。**
API Key 要在空间里创建、按 capability 白名单授权，还得管密钥生命周期；一期是
单机命令行、一个人用，`.env` 里的邮箱密码换 JWT 足够。将来接服务化要切
`X-API-Key` 时，只需把 `_request` 的认证头从 `Authorization: Bearer` 换掉
（客户端目前只发 Bearer，不支持 API Key）。

**6. 解析是异步的，等就明说。**
`--wait` 轮询 `GET /api/v1/knowledge/:id` 的 `parse_status`
（pending/processing/completed/failed），超时按当时状态报出来，不假装成功。

## 后果

- 索引随时可删库重建；真相源（SQLite + 图片母本）不受任何影响。
- 只有**现行版本**进索引：历史版本的 md 不推，检索要的是「现在有效的那份」。
- 没有 caption 的图、没有简介的视频**仍然进索引**，正文退化成「名称（编号，无描述）」：
  spec §7.1 承诺这类图「仍按编号/项目可查」，退化成编号文本才兑现得了这条。
- 标签随项目名增长；项目改名会在 WeKnora 里留下旧标签，需要定期清理（或直接在
  WeKnora 里改名），这不是真相源的问题。
- 分块粒度由 WeKnora 决定，我们只能通过 KB 的 `chunking_config` 间接影响；
  要按章节精准切分，得等检索效果暴露出真实需求再调。
- 图片目前只推 caption 文本，不推图片向量（WeKnora 的 `image_vector_enabled`
  默认关）。图进入向量空间是第二阶段的事。
- **embedding 模型钉死**：默认按名字找 `text-embedding-v4`（spec §7.2「从第一天
  定死」），找不到就报错，不静默换成空间里的第一个 embedding 模型。
- **默认建独立知识库**（`052 文档库`），不往既有「项目资料库」里塞：两者标签词表
  不同（那边是 `005-雷达仿真` 这种裸项目名），混在一起会让 `--tag` 语义含糊。
  要合并就显式 `--kb-name 项目资料库`，并接受两套词表并存。
